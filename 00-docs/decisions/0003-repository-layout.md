# ADR-0003: Repository layout: numbered layers, one component shape

- **Status:** Accepted (`talconfig.yaml` in the tree superseded by ADR-0028)
- **Date:** 2026-10-20
- **Deciders:** Stan (owner), Claude (proposer)
- **Related:** ADR-0002, ADR-0004, ADR-0013, ADR-0015

## Context

Stan wants a repo where the top level shows only ordered folders, and where every part looks the same. This avoids scattered files, hidden config, and one-off structures. The layout must hold for 1 to 7 nodes and for many apps without any restructuring.

## Decision

### Tree

```
olympus/
├── 00-docs/                  # read first
│   ├── architecture.md       # living: how the system works now
│   ├── conventions.md        # living: the rules, each linked to its ADR
│   ├── inventory.md          # GENERATED: components, versions, namespaces, nodes. Never hand-edit.
│   ├── decisions/            # ADRs (ADR-0000)
│   └── runbooks/             # NN-<phase>.md + task runbooks (break-glass.md, restore.md, add-node.md)
├── 01-talos/                 # layer 1: node OS
│   ├── talconfig.yaml        # single source of nodes, IPs, labels, disks, schematics, Talos/K8s version
│   ├── talsecret.sops.yaml
│   ├── patches/{global,controlplane,worker}/*.yaml
│   └── clusterconfig/        # GENERATED by talhelper, git-ignored
├── 02-bootstrap/             # layer 2: run once per cluster build
│   ├── helmfile.yaml.gotmpl  # cilium → flux-operator → flux-instance, values read from layer 3/4 files
│   └── resources/            # flux-system namespace, sops-age secret template, deploy-key secret
├── 03-cluster/               # layer 3: the Flux entrypoint and cluster-wide primitives
│   ├── kustomization.yaml
│   ├── cluster-settings.yaml # the only shared values (ConfigMap used for postBuild substitution)
│   ├── layers.yaml           # one Flux Kustomization per 04-platform group, plus 05-apps, chained by dependsOn
│   ├── priority-classes.yaml
│   ├── components/           # reusable kustomize components (default-deny, backup, …)
│   ├── flux-operator/
│   └── flux-instance/
├── 04-platform/              # layer 4: shared infrastructure, groups in dependency order
│   ├── 01-network/           # gateway-api-crds, cilium, gateway, tailscale, cloudflared, external-dns
│   ├── 02-storage/           # local-path-provisioner, k8up
│   ├── 03-security/          # admission-policies
│   ├── 04-observability/     # metrics-server, victoria-metrics, ntfy-alertmanager, kite
│   ├── 05-operations/        # tuppr

├── 05-apps/                  # layer 5: Stan's services, one folder = one namespace
├── .claude/                  # CLAUDE.md, settings.json, skills/
├── .github/                  # README.md (repo front page), CODEOWNERS, workflows/, checks/,
│                             #   sync-rules.yaml, pull_request_template.md, renovate.json5

├── .sops.yaml
└── .gitignore
```

### Rules

1. **The root holds only the numbered folders and the hidden entries listed above.** Those hidden entries are required at the root by the tools themselves: Claude Code, GitHub, mise, and sops. Nothing else is ever added at the root.
2. **Numbers express dependency order.** A layer depends only on lower-numbered layers, and a group inside `04-platform/` depends only on lower-numbered groups.
   - The set of layers and groups is closed. A new component joins an existing group.
   - A genuinely new group is appended with the next number. Nothing is ever renumbered.
3. **Every component, in `03-cluster/`, `04-platform/`, or `05-apps/`, has exactly this shape:**
   ```
   <component>/
   ├── ks.yaml                 # Flux Kustomization(s): path ./app, dependsOn, namespace, olympus/* annotations
   └── app/
       ├── kustomization.yaml
       ├── namespace.yaml      # if the component owns its namespace (Pod Security labels live here)
       ├── ocirepository.yaml  # chart source, pinned
       ├── helmrelease.yaml
       ├── values.yaml         # Helm values; HelmRelease reads it via configMapGenerator; bootstrap reads it too
       └── *.sops.yaml         # secrets, if any
   ```
   - `ks.yaml` sits outside `app/` so that it never applies itself.
   - A `ks.yaml` may define several Kustomizations only when CRD ordering requires it, for example `cilium` and then `cilium-config` for the IP pools.
   - Non-Helm components replace `ocirepository.yaml` + `helmrelease.yaml` with plain manifests, but keep the same files otherwise.
   - A component that builds its own container image (for example Athena) adds `image/` (Dockerfile and image-only files) next to `app/`. This is the only allowed extra folder.
4. **The namespace equals the component folder name.** The only exceptions are the ones upstream requires: `cilium` and `metrics-server` run in `kube-system`; `flux-operator` and `flux-instance` run in `flux-system`.
5. **Each group folder has a `kustomization.yaml` that lists its components' `ks.yaml` files.** Nothing is discovered implicitly.
6. **Cohesion: everything about X lives in X's folder.** That includes its secrets, dashboards, alert rules, network policies, and its external config. Examples: the tailnet policy file sits in `tailscale/`, and Athena's Dockerfile sits in `athena/`.
7. **Folder and file names are lowercase kebab-case with no spaces.** Only layers and groups carry a `NN-` prefix.
8. **Every YAML manifest starts with a `# yaml-language-server: $schema=…` line** where a schema exists.

## Consequences

- Any component can be understood by opening one folder, and every folder looks alike.
- Adding an app is a copy of a known shape (the `add-component` skill).
- The layout matches the home-operations pattern (`talos/`, `bootstrap/`, `kubernetes/`) one-to-one, so community examples carry straight over.

## Alternatives considered

- **`00. Documentation` style names:** spaces and dots break unquoted paths in Flux, kustomize, CI globs, and shell. Rejected.
- **Grouping namespaces by function (`network`, `observability`), as home-ops does:** fewer namespaces, but weaker isolation and RBAC granularity. Rejected in favor of namespace = component.
- **Separate `infrastructure/` and `apps/` repos:** duplicated tooling, and changes that span both get split across repos. Rejected.

## Compliance

- `component-shape` verifies every component folder against rule 3, plus the namespace rule 4.
- `orphans` checks that every `ks.yaml` is referenced by its group, and that every reference exists.
- `root-clean` checks that the root contains only the allowed entries.
